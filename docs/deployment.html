Deployment record · CashMatch

Shipping it

An AI cash application agent, deployed to AWS on free-tier infrastructure, entirely from Terraform. What was built, why it is shaped this way, and the three things that broke.

Live · 13.235.237.109 ap-south-1 · Mumbai 28 resources · Terraform ~₹0/month

01What is live

A public URL serving 800 real payment decisions out of a managed Postgres, with the review queue and the explanation panel working end to end.

81.9% Auto-match rate, live
100% Precision, live
800 Payments decided
28 Terraform resources

Verified by querying the deployed /api/metrics endpoint, not by reading a local number and assuming it carried over.

EndpointWhat it is
http://13.235.237.109The review queue and dashboard
/api/docsInteractive OpenAPI documentation
/api/metricsDashboard figures as JSON
/health, /health/dbLiveness and readiness — reached inside the container network by the Compose health check, not published

The docs page was unreachable, and nothing said so. FastAPI mounts its documentation at /docs by default. nginx proxies only /api and serves the single-page UI on every other path — and because a SPA answers unknown paths with index.html rather than a 404, /docs returned the review UI with HTTP 200. A monitor watching status codes would have seen nothing wrong.

Same shape as the empty database below: a green response over the wrong content. Fixed by mounting the docs under /api/docs — one prefix for everything the API serves, so the UI never has to avoid a path name either — and by a test that fails if either the new path stops answering or the old default comes back.

Plain HTTP, and that is a gap, not an oversight. TLS needs a domain name; an Elastic IP cannot have a certificate issued against it. The honest fix is a domain plus an ACM certificate on a load balancer, and an ALB is the one component here that is not free tier. The deployment is a demonstration, and pretending otherwise by hand-rolling a self-signed certificate would be worse than saying so.

02The shape

Why this shape and not another

ChoiceReasoning
EC2 + RDS,
not ECS Fargate		 Fargate and an Application Load Balancer are the textbook answer and neither is free tier — together about ₹4,000 a month to leave running. For a portfolio deployment the architecture conversation is worth more than the orchestration, and the conversation is identical. What the shape costs is covered under At scale.
RDS,
not Postgres in a container		 A container on the same box would have been simpler and free. RDS buys automated backups, a restore path, and the ability to put the database somewhere the application host cannot be reached from. The free tier covers it, so the simpler option saves nothing.
No NAT gateway At roughly ₹2,700 a month it would have cost more than everything else combined, to give internet access to a database that has no reason to want any. Its absence is a control: a compromised database host cannot exfiltrate anything, because there is no route.
One instance,
not an auto-scaling group		 Defensible only because the instance holds no state. Everything durable is in RDS; the box can be terminated and rebuilt from the Terraform in about four minutes. That is what makes a single instance an acceptable answer rather than a pet.
ap-south-1 Mumbai. The data is an Indian distributor's receivables book and the users would be in India. Latency follows the users, not the engineer.

03Security calls

None of these are expensive. They are the difference between infrastructure that would survive a review and infrastructure that happens to work.

DecisionInstead ofWhy
No port 22,
no key pair		 An SSH ingress rule and a .pem file Shell access is SSM Session Manager. No inbound port to scan, no key to lose or share, and every session recorded in CloudTrail. An open SSH port on a demo box is a liability with no compensating benefit.
Database security group
references the app group
by id		 A CIDR range The rule says "whatever is running the application may reach Postgres", not "anything in 10.0.1.0/24 may". Replace the instance and the rule still means what it meant.
Secrets in SSM
Parameter Store		 A .env file baked into the image The database password is generated by Terraform, written as a SecureString, and read by the instance through its IAM role at boot. It exists in no file anybody edits and in no image layer. Rotating it is a parameter update and a restart.
IAM policy scoped to
two parameter ARNs		 ssm:* on * The instance can read exactly the two values this application owns, and decrypt only via the SSM service. It has no business reading anything else in the account, so it cannot.
IMDSv2 required The default, which still allows v1 Instance metadata v1 is reachable by a server-side request forgery bug in the application; v2 requires a PUT to obtain a token first, which SSRF generally cannot do. One line.
Deployed in
LLM_MODE=mock		 Shipping a live Gemini key Mock mode exercises the entire extraction pipeline with no key and no network. A public demo has no business holding a credential, and the parameter is a deliberate placeholder.
Encryption at rest
on both volumes		 Unencrypted defaults Two booleans. There is no argument for the other choice.

What is still missing, stated plainly: no TLS, because an Elastic IP cannot hold a certificate; no WAF; no authentication on the API, so anyone with the address can approve a review item; CloudTrail and VPC flow logs are off; and the single instance is a single point of failure. Every one of those is a deliberate scope decision for a demonstration rather than an oversight — and an interviewer who asks about any of them deserves this list rather than a surprise.

04Build and release

Images are built on a developer machine and pulled by the instance. A deploy is therefore a pull, never a build.

Two reasons, and the second is the real one. A t3.micro has 1 GB of RAM, which is comfortably enough to run this stack and nowhere near enough to run npm ci and a Vite build. And more importantly, deploying the exact bytes that were tested is worth more than the convenience of building on the target: a build that happens twice can differ twice.

./deploy.sh

  --> authenticate to ECR
  --> docker build -f backend/Dockerfile.prod   548 MB  (124 MB compressed)
  --> docker build frontend                      74 MB  ( 21 MB compressed)
  --> docker push  ×2
  --> aws ssm send-command  "systemctl start cashmatch-refresh"
        which runs: docker compose pull && docker compose up -d

The release step is an SSM command rather than an SSH script, for the same reason there is no port 22. It is auditable and needs no credentials on the developer machine beyond the ones AWS already has.

Two production-readiness changes the deploy forced

ChangeWhy it was needed
Settings normalises
postgres://		 Render, Heroku, Railway and Fly all emit postgres://. SQLAlchemy 2.x dropped that alias and this project pins psycopg 3, so the URL needs an explicit driver. Normalising in one place rather than asking every deployment to hand-edit an environment variable is what makes the same image run anywhere.
A self-seeding
entrypoint		 A managed platform gives you one process and no shell during a deploy. The entrypoint runs migrations, seeds the demo dataset only if the database is empty, and then serves. A fresh deploy comes up with data in it; a restart changes nothing.

Both changes also made the project deployable to Render from the same repository — a render.yaml blueprint is committed alongside the Terraform. Portability was not the goal; it was the by-product of not hard-coding assumptions about one host.

05What broke

Three failures, and only one of them was a bug. Telling them apart was most of the work.

1. The network, twice — not a bug

A 548 MB image push died with write: broken pipe, and Terraform lost its connection while polling RDS: dial tcp: lookup rds.ap-south-1.amazonaws.com: no such host.

Neither was a configuration problem, and the important move was establishing that before changing anything. Querying AWS directly showed RDS available and the UI image already in ECR — so the state was further along than the error messages implied. The fix was a retry loop around the push, which succeeded on the second attempt. Changing code to fix a dropped TCP connection would have introduced a real bug while chasing a phantom one.

2. Alembic rejecting the database password — a real bug

ValueError: invalid interpolation syntax in
'postgresql+psycopg://cashmatch:WLDr%29Y8I%29X-%7BhvR%28OTO_g1%7D7NnF%7DKS%23D@...'
at position 35

Terraform generates a 32-character password with special characters, and the URL encodes them — %29, %7B, %23. Alembic's env.py passed that URL to config.set_main_option(), which routes through Python's ConfigParser, which treats % as interpolation syntax and refuses the whole string.

Any securely generated password breaks this. It never surfaced locally because the development password is cashmatch.

The tempting fix is to escape the percent signs, or to restrict the password charset. Both work and both would break again the next time somebody touched that file, because the hazard would still be there.

The fix taken was to stop routing the URL through ConfigParser at all: create_engine(url) directly, instead of engine_from_config() reading the value back out of a parsed ini section. The config file is still used for logging; it is simply no longer asked to carry a secret it was never designed to hold.

3. A live site with an empty database — the worst kind

The deploy came up healthy, served HTTP 200, and reported zero payments. Nothing errored anywhere.

The bootstrap script wrote a compose file with a command: override that ran migrations and started uvicorn — which silently replaced the image's entrypoint, the thing that does the seeding. Two mechanisms for the same job, one quietly shadowing the other.

This is the failure mode worth dwelling on in an interview. A crash is cheap: it tells you where to look. A green health check over an empty database tells you nothing, and would have been found by a user rather than by the deploy.

An Elastic IP is free only while attached to a running instance. Detach it, or stop the instance and leave the address allocated, and it starts billing immediately. It is the single most common way a "free" AWS account quietly starts charging, which is why the address is bound to the instance in Terraform rather than allocated loose.

terraform destroy removes all 28 resources and returns the bill to zero. That is the real argument for infrastructure as code on a personal account: not reproducibility, but a reliable off switch.

For comparison, the ECS Fargate and ALB shape would run about ₹4,000–5,800 a month and none of it is free tier — the load balancer alone is roughly ₹1,600 whether anything is using it or not.

07Runbook

Stand it up from nothing

cd infra
terraform init
terraform apply -target=aws_ecr_repository.api -target=aws_ecr_repository.ui
cd .. && ./deploy.sh      # build and push, so images exist before the instance boots
cd infra && terraform apply

Ship a change

./deploy.sh                # build, push, and roll the instance

Get a shell — no SSH, no key

aws ssm start-session --target $(terraform -chdir=infra output -raw instance_id)

When the site does not answer

/var/log/user-data.log                      # bootstrap; always look here first
cd /opt/cashmatch && docker compose ps     # are both containers up and healthy?
docker compose logs api --tail 50          # the API is what fails; nginx rarely does

Reseed the demo data

docker compose exec api python -m cashmatch.cli generate --reset
docker compose exec api python -m cashmatch.cli extract
docker compose exec api python -m cashmatch.cli apply

Turn the bill off

cd infra && terraform destroy

What this deployment would need to become if it carried a real distributor's receivables, roughly in the order the pain would arrive.

TLS and a domain Route 53 plus an ACM certificate on an ALB. First thing, and non-negotiable the moment anyone types a password into this. Currently blocked only by the fact that a certificate cannot be issued for a bare IP.
Authentication Right now anyone with the address can approve a review item and move cash. Cognito or an OIDC provider, mapped onto the reviewed_by field the schema already carries.

09Questions this invites

Why not ECS or Kubernetes?

Cost, and honesty about what the deployment is for. Fargate plus an ALB is about ₹4,000 a month with nothing on it, and this is a portfolio demonstration that should cost nothing to leave running.

The architectural reasoning does not change: the application is stateless and containerised, all state is in RDS, and configuration comes from the environment. Moving to ECS is a change of runtime, not a redesign — which is itself the thing worth demonstrating. Kubernetes for one service with one instance would be a costume, not an architecture.

A single instance is a single point of failure. Why is that acceptable?

Because the instance holds nothing. Everything durable lives in RDS; the box runs two containers pulled from ECR and configured from SSM. Terminate it and Terraform rebuilds an identical one in about four minutes.

That is the property that separates a disposable instance from a pet, and it is worth being precise about: the problem with a single instance is not that it can die, it is that dying might lose something. Here it cannot. For production I would still want an auto-scaling group across two AZs behind a load balancer — but for availability, not for data safety.

Why is there no NAT gateway?

Because nothing needs one. The only thing in the private subnets is RDS, which has no reason to originate a connection to the internet. A NAT gateway would have cost roughly ₹2,700 a month — more than every other resource combined — to provide a capability that is a liability.

Its absence is a security control as much as a saving. There is no route out of those subnets, so there is no exfiltration path, regardless of what any application bug might want to do.

How do you get a shell on the box?

SSM Session Manager: aws ssm start-session --target i-05652e7f3b8058075. There is no inbound port 22 and no key pair at all.

It is better on three counts and worse on none. Nothing to scan, because the port does not exist. Nothing to lose, because there is no private key. And every session is recorded in CloudTrail with the IAM identity that opened it, which an SSH key shared between two engineers can never tell you.

Walk me through a failure you hit.

The one worth telling is the third, because nothing went wrong visibly. The deploy succeeded, the health check was green, and the site served an empty database.

The bootstrap script wrote a compose file with a command: override that started the server directly — which silently shadowed the image's entrypoint, the thing that runs migrations and seeds. Two mechanisms doing the same job, one quietly winning.

A crash would have been cheaper: it points at a line. A green health check over an empty database points nowhere, and in a real deployment would have been found by a user rather than by me. The fix was to delete the override and let one mechanism own startup.

Something is broken in production. What do you do first?

Establish whether the thing that looks broken actually is. On this deploy two of three failures were a dropped TCP connection wearing a config error's clothing — and querying AWS directly showed the state was further along than the error implied.

Then, in order: /var/log/user-data.log for anything at boot, docker compose ps for container health, docker compose logs api for the application. The API is what fails; nginx serving static files almost never does.

Changing code in response to a network error is how a real bug gets introduced while chasing a phantom one.

What would you fix first if this were real?

TLS and authentication, in that order, and before anything architectural. Right now the traffic is plaintext and anyone with the IP address can approve a review item — which in this application means moving money against a customer account.

Everything else on the list — Multi-AZ, ECS, CI/CD, observability — is about scale and operability. Those two are about whether it should be reachable by the public at all.

How much did this cost?

Nothing. Every resource is free-tier eligible except about ₹1 a month of ECR storage above the 500 MB allowance.

The thing to watch is the Elastic IP: free while attached to a running instance, billed the moment it is not. That is the most common way a free AWS account quietly starts charging, which is why it is bound to the instance in Terraform rather than allocated loose — and why terraform destroy exists as a reliable off switch rather than a cleanup chore.
